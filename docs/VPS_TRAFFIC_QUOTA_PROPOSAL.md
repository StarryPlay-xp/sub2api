# VPS 整机流量套餐监控：需求与方案讨论稿

最后更新：2026-11-02

> 最终方案以 [本机流量套餐监控交接文档](HOST_TRAFFIC_QUOTA_HANDOFF.md) 为准。本文保留为历史讨论稿；下文的独立采集程序、设备注册、多机管理和上报设计均已不采用。现方案只统计运行 sub2api 的本机，由进程内直接采集。

状态：历史讨论稿，已由本机采集方案替代；不作为当前实现依据。

## 1. 文档目的与结论

用户希望在本项目管理后台的流量监控面板中，查看一台或多台 VPS 的整机套餐消耗，例如“每月 1.5 TB、双向计费，本周期已用多少、还剩多少”。被监控 VPS 上的流量是否由本项目产生，不影响统计范围。

技术上可实现。建议由本项目提供独立的主机采集程序，在 VPS 上读取公网出口网卡的收发计数，将记录上报给本项目后端，保存历史并按套餐周期汇总，由前端展示用量。

服务商接口不作为功能前提。用户明确指出服务商众多、接口支持不一致，因此依赖服务商接口无法成为通用主方案。以后可以增加服务商数据源作为可选校准方式。

产品上不应把所有计算参数都作为首次接入必填项。建议采用“连接设备 → 配置套餐 → 可选补全本期用量”的流程，系统自动获取技术信息，明确显示数据完整性。

## 2. 已确认需求与尚未确认的建议

### 已由用户明确的需求

- 统计 VPS 整台机器的流量，与流量是否经过本项目无关。
- 在本项目管理后台的流量监控面板展示套餐总额与本周期消耗。
- 支持按 VPS 套餐的计费方式、流量重置周期计算；双向计费是当前实例。
- 核心能力不能依赖所有服务商都提供流量查询接口。
- 需要从产品角度控制用户填写的信息量，而非直接暴露全部后端参数。
- 当前要求是整理文档，供另一个 Agent 讨论需求和方案。

### 本文提出、仍待讨论的建议

- 使用独立主机采集程序主动上报。
- 将 VPS 作为独立设备管理，不强制绑定 WireGuard 节点或本项目的部署实例。
- 普通套餐表单突出额度、计费方向、重置规则三项。
- 月中接入允许可选补全本期已用量。
- 以明确的文字区分本期完整统计、本期估算、接入以来统计与数据缺口。
- 第一阶段优先支持 Linux、按月重置及基本网卡拓扑。

以上建议不能视为用户已经确认的最终范围或部署授权。

## 3. 统计范围

“整机流量”在本需求中指 VPS 上所有程序经过套餐计费网络出口的收发流量，包括网站、文件传输、代理、系统更新、容器等产生的公网通信。

需要选择正确的统计边界：

- 统计承载套餐流量的公网出口网卡。
- 避免把公网网卡、Docker 桥接网卡、容器虚拟网卡、WireGuard 隧道网卡重复相加。
- 回环通信和不计费的独立内网接口不应算入公网套餐消耗。
- 公网与免费内网共用同一网卡、多网卡、策略路由、网卡绑定等情况，需要进一步识别或限制支持范围。
- IPv4 和 IPv6 若共用同一出口网卡，其流量已经包含在该网卡计数中，不应再分别相加一次。

主机网卡统计能覆盖整机通信，但不保证与服务商账单完全相等。计量位置、免费流量规则、封装和数据更新延迟等可能造成差异。界面应说明数据来源为“主机采集”；“完整”仅指本系统观察覆盖完整，不表示服务商账单已核对。

本项目已有应用服务流量、WireGuard 隧道流量、历史查询、图表及带宽参考上限配置，但没有独立的 VPS 整机套餐采集与账期管理功能。

## 5. 建议的用户操作流程

### 5.1 连接设备

1. 管理员在流量监控面板点击“添加 VPS”。
2. 后台生成设备注册信息和安装命令。
3. 用户在目标 VPS 上执行命令。
4. 采集程序完成注册并上报设备基本信息、候选出口网卡及初始计数。
5. 后台显示设备在线，用户可修改自动生成的设备名称。

正常流程不要求在后台填写 SSH 地址、SSH 密码或私钥。SSH 只是用户执行安装命令的一种方式，产品不需要持有远程登录凭据。

公网网卡应自动识别，无法可靠判断时才要求用户选择。多出口或特殊网络结构不能靠静默猜测完成配置。

### 5.2 配置套餐

| 项目 | 建议交互 | 是否普通必填项 |
| --- | --- | --- |
| 周期流量额度 | 数值＋GB／TB，例如 1.5 TB | 是，启用套餐展示时需要 |
| 计费方向 | 接收＋发送／仅发送／仅接收，均以 VPS 为参照 | 是 |
| 重置规则 | 每月 1 日／每月指定日期；其他规则另行讨论 | 是 |
| 设备名称 | 自动生成，可修改 | 否 |
| 重置时刻与时区 | 周期详情中可修改，主界面显示生效规则 | 不作为独立阻塞步骤，但必须可见、可确认 |
| 字节换算规则 | GB／TB 的精确换算放高级设置 | 否，提供明确默认并允许修改 |
| 统计网卡 | 自动识别；有歧义时引导选择 | 通常否 |
| 订阅开通时间 | 不要求填写，使用实际额度重置规则 | 否 |

如果采用默认时刻和时区，应显示“按默认规则统计”，不能表示服务商规则已确认。例如“每月 24 日 · UTC 00:00（默认，可修改）”。默认 UTC 00:00 本身仍是待讨论的产品选择。

“一个月”不等于固定 30 天。每月 29／30／31 日遇到短月时如何处理，需要有明确规则；应从原始重置日计算，避免日期逐月漂移。

### 5.3 月中接入与可选校准

月中接入时不能从一个当前网卡累计值还原此前整个账期的流量。接入完成后，建议提示：

> 已开始统计。这台设备在本周期中途接入，之前的流量尚未包含。
>
> 补充本期已用量 / 从现在开始统计

若用户选择补充，只要求填写服务商面板刚刷新的已用量及显示单位。后台自动选择对应的最新采集基准和时间，不要求用户手填“校准时间”。

设计约束：

- 如果设备离线或上报已经过期，先等待有效的新数据，再建立校准基准。
- 服务商数字可能经过舍入或延迟更新，因此此方式产生的是估算起点。
- 校准后用“校准值＋基准之后新增的计费方向流量”计算本期用量。
- 再次校准应替换该周期的计算基准并保留记录，不能把两次输入的已用量相加。
- 只输入双向合计时，无法还原校准前接收／发送各自的数值；页面只能显示接入后的方向明细，不能伪造完整周期的方向拆分。
- 用户也可以不校准，功能仍可使用，从接入时开始统计。
- 若 VPS 已有可信历史，未来可考虑导入；不建议作为首版必需能力。

## 6. 页面展示与数据可信度

建议在流量监控页增加“VPS 套餐流量”区域。其账期由每台设备自己的套餐规则决定，不应随现有应用流量的“最近 24 小时／7 天”等筛选器悄悄变化。

每台设备建议展示：

- 设备名称、连接状态、最后上报时间。
- 本周期起止时间、下次重置时间。
- 套餐额度、当前已用量、使用比例。
- 适用时显示剩余额度；超额时显示超出量。
- 可获得范围内的接收／发送明细和趋势。
- 数据来源、是否校准、是否存在统计缺口。

| 实际数据情况 | 主文案 | 剩余额度如何呈现 |
| --- | --- | --- |
| 月中接入，未补充之前用量 | 接入以来已用；本期数据不完整 | 不显示可信的本期剩余值 |
| 用户补充了期初缺失部分 | 本期估算已用 | 标为估算剩余 |
| 从周期开始持续采集且无已知缺口 | 本期已用（主机采集） | 按主机计量结果计算 |
| 有无法恢复的采集缺口 | 显示已记录量并提示缺口 | 降低可信度，不伪装成完整余额 |
| 设备上报中断 | 保留最后数值，显示离线／数据未更新 | 不补零、不暗示仍实时更新 |

校准状态、覆盖完整性、在线状态是不同维度，应分别保存。设备可以同时“已校准、离线”，也可以“在线但历史有缺口”。

页面示例，以下数值仅为设计示例：

> VPS-A · 双向计费
>
> 本期估算已用 102.92 GB / 1.50 TB · 6.86%
>
> 下次重置：11 月 24 日 · UTC
>
> 已人工校准 · 最近上报 30 秒前

## 7. 技术方案建议

```mermaid
flowchart LR
    A[VPS 公网出口网卡] --> B[主机采集程序]
    B --> C[本地持久化记录]
    C -->|加密连接主动上报| D[本项目设备上报接口]
    D --> E[数据库与账期汇总]
    E --> F[管理后台流量监控面板]
```

### 7.1 主机采集程序

- 首版建议以 Linux 为目标；读取系统提供的网卡收发累计计数，不解析业务内容。
- 推荐作为主机后台服务运行，避免误把普通 Docker 容器的网络视图当作整机视图。
- 本地持续保存记录，本项目后端暂停或网络断开时继续采集，恢复后补报。
- 以稳定设备身份、启动标识、网卡身份和记录序号识别重启、网卡重建及重复记录。
- 采样与上传频率分开设置；具体频率需根据账期边界精度、磁盘写入成本和设备数量确定。
- 采集不是限速功能，不应修改路由、WireGuard 配置或业务防火墙。

### 7.2 上报与后端存储

- 每台设备使用独立凭据，权限仅限该设备的采集上报，不授予管理权限。
- 注册凭据与长期上报凭据的生命周期应明确，支持撤销、更换；凭据不写入普通日志。
- 上报接口独立于管理员浏览器接口认证，不要求采集程序持有管理员登录令牌。
- 使用设备身份和记录序号等唯一键去重；确认落库后再允许客户端清理已确认记录。
- 允许离线补报、重复提交及受控的乱序到达，禁止同一段流量重复累计。
- 限制单次上报体积、频率与可接受时间范围，校验异常计数及设备时钟偏差。

建议的逻辑数据实体：设备、套餐规则版本、采集记录、周期汇总、校准记录、数据缺口。最终表名和接口契约由实现方案确定。

套餐额度和周期规则变更需要保留语义：默认不应悄悄重算所有已关闭历史账期；“立即生效”与“下期生效”的交互待讨论。

### 7.3 计数连续性与周期边界

累计计数的差值用于计算新增流量，但实现不能只在内存中保存上一次值。

- 程序重启：从持久化状态恢复，防止重复和丢失。
- 机器重启或网卡计数重置：识别新的计数阶段，不能把下降值当成负流量，也不能把新值与旧阶段直接相减。
- 突然断电：最后一次保存到断电之间的尾部可能无法恢复，需要标记；不能宣称完全无损。
- 采集停止但网卡计数未重置：可能恢复期间总增量，但未必能恢复其时间分布。
- 离线期间跨越账期边界：依靠本地时间记录补报分配；只有一个跨界总增量时，不能假装知道两期各占多少。
- 周期边界附近应安排采样或保存边界基准；剩余时间误差应有明确处理方式，不能无说明地按比例插值当作精确值。

每月重置应创建新统计区间、保留历史，不清空网卡计数或删除采集历史。没有缺口且从新周期开始持续记录时，新周期不再需要继承上期人工校准值。

## 8. 历史可行性观察（去标识摘要）

早期讨论曾进行单台 Linux 主机的只读可行性检查，连接信息来自用户当时提供的信息。公开文档仅保留结论，不保存主机信息、网卡标识、实际流量读数、套餐截图值或连接凭据。

当时可以读取网卡累计计数并观察增量；这只能说明计数读取可行，不能证明当前账期完整，也不能代替容器宿主机挂载、持久化、重启连续性、去重或账期切换验收。服务商页面的准确重置时刻、底层单位和数据延迟仍需由用户确认。

这些是早期讨论的历史记录，**本次后端实现没有连接或操作服务器，也没有重新验证上述环境**。历史授权不沿用到本次实机测试；当前验收边界见交接文档。

## 9. 建议首版范围

建议纳入：

- Linux 主机采集与独立设备注册。
- 明确公网网卡的整机收发统计。
- 本地持久化、断线补报、上报去重和异常状态。
- 额度、计费方向、按月周期、时区与重置时刻配置。
- 可选的本期已用量校准。
- 流量监控页中的 VPS 套餐卡片或列表。
- 周期用量、剩余额度、超额量和数据完整性展示。

建议暂不纳入：

- 所有服务商的接口适配。
- 服务商付费重置、自动购买流量或自动续费。
- 自动限速、断网或修改现有代理行为。
- 后台持有 SSH 凭据并自动远程管理服务器。
- 任意复杂网络拓扑、混合计费及多设备共享流量池。
- 跨平台采集、复杂历史导入和消费预测。

以上仅为建议；设备数量、历史保留时长、是否需要通知仍待确认。

## 10. 实现后的验收重点

| 场景 | 应验证的结果 |
| --- | --- |
| VPS 上其他程序产生公网通信 | 能进入整机统计 |
| IPv4／IPv6、容器和隧道通信 | 按公网出口统计，不叠加重复网卡计数 |
| 双向／单向套餐 | 相同采集数据按配置选择计费方向 |
| 月中接入且不校准 | 明确显示接入以来用量，不伪造本期余额 |
| 校准与再次校准 | 新基准生效，无重复累计，来源与时间可追溯 |
| 重复上报、断线后补报 | 已确认数据不重计，记录可补齐 |
| 后端或采集程序重启 | 已保存历史不丢失，新增量连续 |
| 主机重启、网卡重建、异常计数 | 正确区分计数阶段，无法恢复部分有提示 |
| 时区、短月、跨账期离线 | 周期确定且不漂移，不把未知分布当精确值 |
| 设备离线或历史缺失 | 保留已知数值，展示数据状态 |
| 凭据撤销或跨设备上报 | 拒绝无权限请求，不影响其他设备 |

公网传输和重启属于后续实机验证，需要单独确定测试窗口、传输额度和允许影响的服务。本次只读连接授权不代表允许执行这些测试。

## 11. 希望另一个 Agent 重点讨论的问题

1. “连接设备 → 三项套餐配置 → 可选补全”的流程是否足够简单？是否需要先看到设备数据再要求配置套餐？
2. 周期时区和具体时刻采用什么默认值，怎样表达未确认规则而不增加过多认知负担？
3. “本期估算”“接入以来”“本期完整主机统计”的文案和剩余额度展示是否会误导？
4. 独立采集程序是否是本项目适合维护的交付方式，还是复用成熟主机统计工具并增加上报层更合适？两者都不能要求服务商接口。
5. 首版应支持哪些网络拓扑？遇到无法区分的内网／公网流量时，是限制接入还是明确标记估算？
6. 校准如何选择最新采集基准，怎样处理服务商延迟、重复校准和计费规则中途变化？
7. 本地记录、服务器汇总与保留策略如何平衡可靠性、磁盘成本和实现复杂度？
8. 设备套餐区域放在现有流量页的哪个位置？是否需要独立设备详情页？

讨论应先收敛产品语义、首版边界和数据可信度，再确定数据库迁移、接口契约与开发任务。不应将“网卡计数可读取”直接等同于“套餐账单已经可以准确还原”。
