# 本仓库镜像更新
最后更新日期：2026-10-31

管理后台从 `StarryPlay-xp/sub2api` 的 GitHub Release 检查版本。Docker 部署通过宿主机的更新服务拉取 `ghcr.io/starryplay-xp/sub2api`，不再替换容器内的二进制文件。源代码及二进制部署继续使用本仓库的 Release 程序包。

## 支持范围

- Linux、systemd、Python 3.10+、Docker Compose v2；服务名为 `sub2api`、`postgres`、`redis`，三个服务已在同一 Compose 项目中运行。
- 应用连接的数据库必须是该 Compose 项目的 `postgres`，数据库名和用户与 PostgreSQL 容器一致。外部数据库、多副本、任意服务名需要额外适配，当前会拒绝自动更新。
- 只接受严格递增的三段稳定版本，例如 `v0.3.0`、`v0.3.1`。不使用后缀区分定制版本。镜像必须包含正确的版本和源仓库标签。
- 保留原 Compose 项目名、部署目录、全部挂载、数据库及 Redis 容器。配置漂移、备份失败、WG 退出不完整时停止升级。
- 升级期间应用有短暂中断。现有流式请求和 WebSocket 不能跨容器继续。
- 不自动回退程序或数据库。新程序可能已经执行数据库迁移，直接降级可能造成不兼容或丢失新增业务数据。

## 首次接入

首次接入需要维护窗口。先完成下面的文件准备和本地测试，再安装到服务器；这些步骤不是普通版本升级时反复执行的操作。

1. 从本仓库发布完整版本或 Linux amd64 简化版本。Actions 工作流需要仓库内容与 Packages 写权限，发布后的 GHCR package 应设置为公开。不要把服务器凭据或 WG 密钥放入 GitHub Actions。
2. 记录现有应用镜像 digest、Compose 项目名、所有数据挂载和数据库版本。备份现有数据库、应用数据目录、部署配置和密钥。不要用本仓库默认 Compose 文件覆盖现有部署。
3. 将本目录 `updater.py` 安装为 `/usr/local/lib/sub2api-updater/updater.py`，所有者 root，权限 `0755`。将 service 文件安装为 `/etc/systemd/system/sub2api-updater.service`。
4. 将 `compose.image-updater.yml` 放到现有部署目录；它只为应用增加更新 socket 和停止等待时间，不替换数据库配置。更新 socket 目录由更新服务创建，应用只有 socket 使用权，没有 Docker socket 或宿主机备份目录的访问权。
5. 按实际路径填写 `/etc/sub2api-updater.json`，参考 `config.example.json`。`compose_files` 必须包括现有 Compose 文件、更新附加文件，以及已有的 WG 附加文件等；不包含自动生成的 `compose.image-version.json`，程序会自动追加它。
6. `env_file` 指向原有 `.env`。如果部署没有使用 `.env`，可以创建独立空文件供本服务使用，不能覆盖现有环境文件。Compose、环境文件及父目录必须由 root 管理，不得允许普通应用用户修改。
7. WG 密钥仍按 [WG 部署说明](../WIREGUARD_CN.md)配置。使用 `WIREGUARD_KEY_FILE` 环境变量，并将原密钥作为独立文件只读挂载，权限 `0400` 或 `0600`。已有密钥不能重新生成。更新器会单独备份这份文件，后台数据库备份不能代替它。
8. 执行 `systemctl daemon-reload`、`systemctl enable --now sub2api-updater`。随后在维护窗口，把应用首次切换到本仓库已发布版本，并带上上述所有 Compose 附加文件；只重建 `sub2api` 服务。实际首次切换命令应根据核对过的服务器配置生成。
9. 进入后台检查更新服务是否就绪，核对账号、IP 节点和 WG 出口。首次接入前的上游版本不支持新的更新接口，不能从旧后台直接完成这次接入。

示例配置中的 `/opt/sub2api` 只是默认路径，不应覆盖不同部署。`app_gid` 应与镜像内应用用户的组 ID 一致，仓库镜像默认是 `1000`。

### 首次启动导入 WG 并绑定指定账号

需要一并导入 WG 时，先在私密目录运行 `prepare-wireguard-bootstrap.py`，传入原配置文件、安全输出文件、明确的账号 ID 列表和 DNS。例如 `--source /private/path/client.conf --output /private/path/wg-bootstrap.json --account-ids 1,2,3 --name wg-b --dns 1.1.1.1`；ID 必须以实际核对结果为准。

工具只移除 `Table`、`FwMark`、`PostUp`、`PostDown`，在缺少 DNS 时补充指定 DNS，保留隧道密钥等必要字段；不会执行脚本、修改原文件或发起网络请求。输出文件使用 `0600` 且禁止覆盖。原文件和输出文件都不能放进公开仓库或镜像。

在服务器已有 `secrets` 目录中沿用或一次性生成稳定加密密钥，将私密计划以应用用户可读的 `0400` 权限保存，并将 `compose.wireguard-bootstrap.yml` 加入首次启动的 Compose 文件列表。`WIREGUARD_BOOTSTRAP_FILE` 只在应用服务初始化时处理：数据库迁移完成后、调度器及 HTTP 服务启动前，创建节点并绑定全部指定账号。

这是一项严格的一次性部署操作：账号集合必须与计划完全一致、均未删除、无已有代理和影子关系。现有数据库的传输兼容性保护仍然生效。节点、账号绑定及完成标记在同一个事务提交；失败全部回滚并阻止应用启动。完成标记存在后，后续启动直接跳过，不能用它反复强制绑定账号；后续管理应使用后台正常操作。

完成首次导入后，可在受控维护操作中移除 bootstrap 环境变量和计划文件挂载并安全归档计划；长期保留原加密密钥挂载。不要直接删除仍被 Compose 引用的文件。应用运行后的正常业务可能使用新出口；出口连通性及供应商请求验收由人工完成。

## 日常使用

人工合并上游 → 检查迁移冲突和定制功能 → 发布递增版本 → 后台检查更新 → 点击更新。

后台显示下载、关闭、备份、启动和验证阶段。任务由宿主机服务执行，关闭浏览器不会中止任务。新应用自动校验全部 WG 配置能否用原密钥解密，并核对升级前节点仍存在；不主动建立隧道或发起出口探测。已暂停的节点保持暂停，出口连通性和供应商业务验收交给人工。

更新器先检查 GitHub 最新稳定版本，拉取镜像并固定到 digest，然后停止旧应用。确认退出正常、WG 运行占用已释放后才备份。备份位于 `state_directory/<任务ID>/`，包括数据库 SQL 压缩包、应用数据、Compose/环境文件、WG 密钥和旧镜像信息。备份权限受 root 目录保护，不能通过后台下载。

启动新应用后验证镜像、数据挂载、数据库/Redis 容器身份，以及账号、普通代理、WG 配置和绑定的关键字段指纹。指纹异常会标记需要检查，即使它来自合理的数据迁移，也需要人工确认。之后等待应用完成版本及 WG 配置校验，全部通过才显示成功。

`compose.image-version.json` 是 root 管理的已选镜像状态。后续手动 Compose 操作必须继续包含该文件，避免用基础文件里的旧镜像重新创建应用。

## 失败和恢复

- 停止应用之前失败：原服务继续运行，可修复原因后重试。
- 已停止应用、尚未尝试新版本时失败：尝试重新启动原容器，任务仍要求检查，特别是异常退出后的 WG 节点。
- 已尝试新版本后失败：保留新环境、备份和任务状态，不自动恢复旧数据库或旧镜像。检查迁移状态、账号数据和 WG 节点，再制定恢复步骤。
- 更新服务意外退出：下次启动将未完成任务标记为需要检查，不会猜测上次是否执行完毕。
- 需要清除已处理的失败状态时，先停止 `sub2api-updater`，在宿主机执行 `updater.py --config /etc/sub2api-updater.json --acknowledge-failure`，再启动服务。此命令只确认人工已检查，不会替你恢复业务数据。
- 不使用 `docker compose down -v`、删除数据目录或同时重建 PostgreSQL/Redis 来完成应用升级。
- 备份不自动删除。定期核查磁盘容量和备份保留策略，并进行恢复演练；预检查的磁盘估算不能替代磁盘监控。

## 本地验证

```sh
python3 -m unittest discover -s deploy/image-updater -p 'test_*.py' -v
```

此外运行后端 ImageUpdate/UpdateService/SystemHandler 测试、前端 ImageUpdatePanel 测试、类型检查和构建。宿主机可在停止更新服务后运行 `--check` 做部署预检查（会初始化本地任务目录，但不修改容器）；它不代表已经完成真实镜像升级验收。

正式使用前应在隔离环境完成两版本升级与故障演练，包含已有账号、WG 配置/绑定/流量、密钥缺失、备份失败及升级后隧道验证。首次上线应保留原数据与镜像的恢复路径。
